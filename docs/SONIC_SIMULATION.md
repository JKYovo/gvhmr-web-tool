# GVHMR Web → MuJoCo/SONIC 仿真安全流程

## 安全边界

Web 的仿真功能只能启动本机 MuJoCo 和本机 ELF3 仿真控制器。源码中没有 SSH、
`example_demo_hw.launch.py` 或任何真机上电/控制器启动命令。仿真固定使用：

- ROS Domain 73；
- `ROS_LOCALHOST_ONLY=1`；
- SONIC publisher `tcp://127.0.0.1:5557`。

真机 publisher 使用独立的本机 5559，并且真机控制器只能由现场人员按真机
Quickstart 手工启动。后端执行双向互锁：检测到任一真机 SSH 隧道时拒绝启动仿真和
向仿真推流；仿真未完全停止或发现外部仿真进程时拒绝向真机推流。旧的
`5557 → 机器人 5558` 隧道会把仿真端口暴露给机器人，因此两种发送都会被拒绝。

## 页面操作

1. 选择一个已经成功的 Web 任务。
2. 点击“启动仿真”，确认提示仅描述本机 MuJoCo。
3. 等待状态变成“仿真已就绪”。启动顺序是 MuJoCo、ELF3 仿真控制器、`normal`、
   `sonic_teleop`，任一步失败都会停止已启动进程。
4. 先把 SONIC 速度设为较低倍率，再点击“发送到仿真”。
5. 完整检查站立、关节方向、脚步跟踪、自碰、摔倒和停止后的 idle 回归。
6. 点击“暂停 SONIC”可停止当前动作；结束后点击“关闭仿真”。Web 会先停止动作、
   请求 `sonic_teleop → normal`，再依次关闭控制器和 MuJoCo。

推流只允许在 `sonic_teleop` 内进行。播放中通过控制器切到 `normal` 或其他状态时，
接收端会关闭 `smpl_ref` 订阅，Web 在下一发送周期终止并永久作废当前会话。即使随后
重新进入 SONIC，旧动作也不会从中间恢复；页面仍保持错误/停止状态，必须人工重新
点击“发送到仿真”。留在 `normal` 时点击发送会在订阅等待超时后以零帧失败。

关闭完成后状态必须回到“仿真未启动”，并且仿真进程列表为空。不要在仿真运行时
手工建立真机隧道；如果误建，立即关闭隧道并停止仿真。

如果“启动仿真”呈灰色，状态栏会直接显示阻塞原因：旧 5557 真机隧道、5559 真机
隧道，或 Web 之外运行的仿真进程。页面会继续轮询这些外部条件；正常关闭冲突进程或
隧道后，按钮会自动恢复，不需要重启 Web。

## 仿真与真机能否同时开

不能。Web 将仿真和真机设计为互斥目标，而不是两个可并行的终端：

| 项目 | MuJoCo 仿真 | ELF3 真机 |
| --- | --- | --- |
| 谁启动控制器 | Web 仅启动本机仿真 | 现场人员手工启动，Web 无启动能力 |
| ROS Domain | 73 | 31 |
| 本机 SONIC 端口 | 5557 | 5559 |
| SSH 隧道 | 禁止 | `5559 → 机器人 5558` |
| Web 发送条件 | 仿真 `ready` 且无真机隧道 | 仿真完全停止、隔离隧道存在、二次确认 |

仅仅同时打开两个终端不会自动发送数据，但不应同时运行两套控制器或保留真机隧道。

## 已知限制

- ZMQ XPUB 能确认 `smpl_ref` 的订阅/退订，但没有逐帧执行 ACK；Web 显示完成只代表
  发送端完成。
- 当前用户服务没有 `SCHED_FIFO` 权限时，页面会标记“非实时调度”。这种 MuJoCo
  结果可用于动作预检，但不能当作严格的真机时序验收。
- 仿真通过不代表真机必然安全。真机仍需要可靠支撑、实体急停和现场人员，并从短、
  慢、小幅动作开始。

## 只读排查

```bash
ps -ef | grep -E 'elf3_dof29_sim|example_demo.launch.py|simulation_mujoco'
ss -ltnp | grep -E ':5557 |:5559 '
```

仿真运行时允许本机 5557 在动作播放期间监听，但不应出现 5559 监听或任何真机 SSH
隧道。关闭仿真后不应残留 MuJoCo、ELF3 仿真控制器或 SONIC publisher。
